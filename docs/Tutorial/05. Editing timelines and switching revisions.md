# Editing timelines and switching revisions

`beep.Timeline` plays a multi-clip arrangement and can prepare a completely new
arrangement while the current one keeps playing. This is useful for a preview
editor where an in-progress edit must only become audible once every source is
ready.

## Clips

```go
type TimelineClip struct {
	Open     func() (beep.StreamSeekCloser, error)
	Start    int
	In       int
	Out      int
	Duration int
	Gain     float64
}
```

`Start` and `Duration` are measured in output frames, `In` and `Out` in source
frames, and every interval is half-open. Clips may overlap, in which case they
are summed without clipping; gaps are silence. The arrangement length is the
largest `Start+Duration`.

Each `Open` call must return a brand-new reader. Readers are never shared
between clips or between generations, they must support seeking, and `Len` must
be at least `Out`. `NewTimeline` validates the whole table before it opens
anything; if any open or seek fails, readers opened by that attempt are closed.

## Preparing a revision

```go
tl, err := beep.NewTimeline(rate, clips)
if err != nil { /* ... */ }

if err := tl.Schedule(nextClips, at, fade); err != nil { /* ... */ }
```

`Schedule` prepares the whole replacement first. Only after every new reader has
been opened and positioned does it replace the previous pending revision. The
switch happens when output frame `at` is reached, and `fade` frames starting at
`at` cross-fade from the old revision to the new one.

The material position for output offset `k` is computed from the absolute
formula

```
In + k * (Out-In) / Duration
```

with linear interpolation toward the next material frame (clamped to `Out-1`).
This intentionally re-times the clip, changing pitch when `Duration` differs
from `Out-In`; there is no pitch preservation.

## Preparation failures vs. replacement cleanup errors

`Schedule` can fail in two distinct ways, and they mean different things:

- **Preparation failure.** A clip table was invalid, or a new reader could not
  be opened, was too short, or failed to seek. The preparation is discarded and
  **nothing changes**: the audible revision, any revision that was already
  pending, and all of their cursors, read-ahead samples, plans and lengths stay
  exactly as they were. The returned error describes the failed preparation.

- **Replacement cleanup error.** The new revision was prepared successfully and
  is now installed, but closing the revision it replaced failed. The
  replacement **did happen** — the returned error comes from `Close` and must
  not be treated as a failed preparation. The new revision remains pending (or,
  if it is already audible, keeps playing); a cleanup error never resurrects the
  revision that was switched out.

In short: if `Schedule` returns a preparation error, retry with a fixed table;
if it returns a cleanup error, the new revision is live and the error only
reports a release problem.

## Cancelling

`Cancel` removes a pending revision before its switch frame has been output. It
is allowed even after `Position` has reached `at`, as long as that frame has not
been streamed yet. Once a cross-fade has started, `Schedule` is rejected and
`Cancel` reports that there was nothing to cancel.

## Errors while streaming

If a source drains before its `Out` or reports a read/seek error, the timeline
terminates with an error. When some PCM was already produced by the same
`Stream` call, that prefix is returned with `ok == true` and `Err` stays nil; the
error is published on the next non-empty `Stream` call. `wav.Encode` propagates
such an error instead of writing a silently truncated file.
