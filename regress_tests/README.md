# REP string-instruction structured regression

`regression.c` is a self-contained C regression for the 64-bit long-mode
REP string instructions emulated by bdshemu:

| mnemonic | operation | allowed repeat prefixes |
|----------|-----------|--------------------------|
| `MOVS` | `[RDI] = [RSI]` | none, `REP` (F3) |
| `STOS` | `[RDI] = RAX` | none, `REP` (F3) |
| `LODS` | `RAX = [RSI]` | none, `REP` (F3) |
| `CMPS` | compare `[RSI] - [RDI]` | none, `REPE`/`REPZ` (F3), `REPNE`/`REPNZ` (F2) |
| `SCAS` | compare `RAX - [RDI]` | none, `REPE`/`REPZ` (F3), `REPNE`/`REPNZ` (F2) |

Element widths are 1, 2, 4 and 8 bytes. The test only calls `NdDecodeEx` and
`ShemuEmulate`; it never runs real machine code, never invokes NASM and does
not use the Python test framework. The production library sources are not
modified.

## The two independent implementations

Every test scenario is first expressed as an **operation plan**
(`PLAN` / `PLAN_OP`). The same plan then drives two completely separate
implementations:

1. **Independent model** (`ref_run`). A small element-by-element interpreter
   written only for this test. It computes every expected memory access,
   pointer move, RCX transition, accumulator change and arithmetic flag from
   the plan fields and the initial byte image. It never reads the decoded
   `INSTRUX` operand fields to derive expectations; the decoder output is used
   only by `code_decodes_cleanly` to prove the generated bytes decode.
2. **Production emulator** (`emu_run`). The plan is encoded into x86-64
   machine code and executed by `ShemuEmulate`. External data is reached only
   through the bounded `AccessMemory` callback.

The two runs are compared event by event (see below). Every enumerated plan
is executed twice, on freshly allocated emulator contexts and independent
reference/emulator memory images, so one mutable buffer can never validate
itself. The small dedicated witness plans use separate reference and
emulator byte images as well.

## Plan encoding

A `PLAN_OP` records, per string instruction:

* `Ins` (`OP_MOVS..OP_SCAS`), `Prefix` (`PFX_NONE/REP/REPE/REPNE`),
  `Width` (1/2/4/8) and `Df` (the direction flag for the op);
* source/destination region (`A`/`B`/`C`) and slot/byte offset;
* `Count` (initial RCX), the planned low accumulator byte `Acc`, and the
  optional callback-failure injection (`InjectFail`, `FailEvent`).

`plan_encode` turns each op into this deterministic instruction stream
(long mode only):

```
REX.W B8+rd imm64     mov rsi, <source linear address>
REX.W B8+rd imm64     mov rdi, <destination linear address>
B9 imm32              mov ecx, <count>
REX.W B8+rd imm64     mov rax, (ACC_SENTINEL << 8) | Acc   (unless KeepAcc)
FC / FD               cld / std
[F3/F2] [66] [48] op  the string instruction
```

The string opcode is the byte form (`A4/AA/AC/A6/AE`) for width 1 and the
wide form (`A5/AB/AD/A7/AF`) otherwise, with `66` selecting 16-bit and `48`
(REX.W) selecting 64-bit operands. F3/F2 are emitted only for prefixes the
architecture allows for that instruction.

The reference model's addresses are computed from the same region/offset
fields, so identical addresses are arrived at independently of the encoder.

## Memory model and recorded events

Three fixed, non-overlapping virtual ranges are used:

* code:   `0x200000`, size `0x2000`;
* stack:  `0x100000`, size `0x4000`;
* external data: `0x400000`, split into regions A/B/C of 64 qwords each.

The `AccessMemory` callback only honors addresses inside the external data
range and records each access as a `MEM_EVENT`: linear address, width,
direction (read/write), the bytes observed, the owning plan operation and the
element iteration. Writes are applied to the backing byte array immediately,
so every later read observes the newly stored value. A plan can arm exactly
one read to be rejected; the callback then returns false, which makes
`ShemuMemLoad` report `SHEMU_ABORT_GLA_OUTSIDE`, and no event for that access
is committed.

`MOVS` is modeled as an explicit per-element **read then write** sequence
(no `memcpy`/`memmove`), which makes overlapping source/destination behavior
match the emulator element for element, including identical regions and
regions differing by one element, in both DF directions.

## Repeat, direction and termination semantics in the model

* If RCX is zero on a repeated instruction, no data access occurs and the
  pointers, accumulator and flags are left exactly as they were on entry.
* Otherwise each element is processed, then RCX is decremented once.
  `REPE` stops at the first element whose comparison clears ZF; `REPNE` stops
  at the first element that sets ZF. The element that causes the stop is
  fully consumed (it is compared and RCX/pointer updates for it are visible).
* `DF=0` advances RSI/RDI by the element width; `DF=1` subtracts it.
* `MOVS`/`STOS`/`LODS` never modify the arithmetic flags.

## Independent flag computation

For a width-sized subtraction `a - b` (`CMPS`: source minus destination;
`SCAS`: accumulator minus destination), `sub_flags` masks both operands to
the element width and computes, independently of the library:

* **ZF**: result is zero.
* **SF**: the result sign bit (top bit of the width) is set.
* **CF**: unsigned borrow, i.e. `a < b`.
* **OF**: signed overflow, `(sign(a) && !sign(b) && !sign(r)) ||
  (!sign(a) && sign(b) && sign(r))`.
* **PF**: even parity of the low eight bits, using the same 4-bit popcount
  table approach as the emulator.
* **AF**: set when bit 4 borrows, `((a ^ b ^ r) & 0x10) != 0`.

Only CF, PF, ZF, SF, OF and DF are compared (`ARITH_MASK` plus DF). AF is
computed by the model for documentation but **excluded from comparison**
because the current production emulator never assigns AF on the string
compares; treating it as undefined here keeps the test honest about that
behavior. The reserved RFLAGS bit 1 and the initial arithmetic flags are
seeded to known values so that flag-preserving instructions and RCX==0 cases
are checked against real, non-zero bits.

## Stop reasons and partial updates

The instruction budget (`MaxInstructionsCount`) is deliberately large so it
is never the cause of a stop. Plans instead end in one of two explicit ways,
both asserted:

* one byte past the shellcode region, giving `SHEMU_ABORT_RIP_OUTSIDE`;
* a trailing `UD2`, giving `SHEMU_ABORT_CANT_EMULATE`.

When a callback read is rejected, the test records the library's actual
partial-update convention (for example, on `CMPS` the source read advances RSI
but RDI, RCX and the flags are not updated because the destination read never
happened). It does not assume whole-instruction rollback.

## Coverage and what is intentionally not covered

Included:

* deterministic enumeration with a fixed seed, currently **152 distinct
  executed plans** (the required minimum is 128), including plans where two or
  more string instructions operate on the same data region;
* all five instructions, all four widths, all three legal prefixes, both DF
  directions, overlapping/adjacent MOVS regions, accumulator chains
  (`STOS`/`LODS` feeding `CMPS`/`SCAS`);
* first-element stop, last-element stop, all-equal runs, highest-bit borrow,
  parity and overflow flag vectors, and ZF left over from a prior compare;
* RCX == 0 freeze behavior, explicit stop reasons, callback rejection with
  the committed access prefix and partial register state, and dual-context
  replay on independent buffers.

Not covered in this round (these are not new mechanisms under test):

* address-size override prefixes and non-64-bit address/operand sizing;
* segment base addresses and segment overrides (flat segment model assumed);
* AF equality against the emulator (the library does not produce AF here);
* 16-bit and 32-bit processor modes;
* any instruction outside the five string operations, except the small
  `MOV`/`CLD`/`STD`/`UD2` support instructions used to build the plans;
* interruptibility, exception delivery and REP restart semantics.

## Logging and mutation wiring

A run prints a `SUMMARY plans_executed=... first_diff='...' op=... event=...`
line so the number of plans, the first differing event and its operation
number are always visible in the log; per-plan failures additionally print a
`PLAN_FAIL` line. The three dedicated cases
(`rep_counter_witness`, `rep_direction_witness`,
`rep_termination_witness`) use `UNIT_CHECK_TAG` with the `counter`,
`direction` and `termination` tags so the matching patches under
`support/mutations` are rejected by their named assertion.
