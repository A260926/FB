# 稳定覆盖反馈：复测、缩减与准入的衔接

本文说明 Worker 复测（replay）、缩减（minimize）与 Hub 准入（admission）
之间的证据流转约定。相关代码在 `worker.go`（`observeStable`、
`triageInput`、`minimizeInput`）和 `hub.go`（`notePending`、
`withdrawPending`、`confirmPending`、`handleNewInput`）。

## 稳定覆盖的定义

同一个候选连续执行 3 次（不重试、不更换进程策略），覆盖计数按槽位取
**最小值**，零参与取最小；优先级（Fuzz 返回值）按现有约定取**最大值**；
执行时间取**最小值**。3 次里只要有一次崩溃/挂起，候选走现有 crasher
通道；只要有一次返回负数，候选整体作废，不能进 corpus。得到的覆盖切片
是候选自己的副本，不引用会被下一次执行覆盖的共享内存。分桶
（`roundUpCover`）只在证据合入 Hub 时做，Input 里保留原始计数。

## 临时占位（pending）的生命周期

Hub 里有两份严格分开的覆盖：

- **已确认覆盖** `ROData.corpusCover`：只被 `handleNewInput` 接受输入时
  更新，一旦写入不会被撤回。
- **临时占位** `Hub.pending`：以候选数据的 hash 为键、按桶存储的覆盖，
  仅用于抑制“蜂拥排队”。对外展示的 `maxCover` 永远是
  `corpusCover ∪ pending` 的重算结果，而不是独立累积的状态。

占位只有两个出口：

1. **转确认（confirm）**：候选通过复测（和可能的缩减）后由
   `handleNewInput` 接受进 corpus。此时它的覆盖已经并入
   `corpusCover`，占位条目删除并重算 `maxCover`。确认覆盖不依赖占位
   条目存在，因此先撤回后确认的交错也不会丢覆盖。
2. **释放（withdraw）**：候选在复测中崩溃/挂起、任一 run 返回负数、
   复测后相对 `corpusCover` 不再有新覆盖，或到达 Hub 时发现已被别人
   覆盖/签名重复。占位删除并重算 `maxCover`，之后能稳定覆盖这些槽位
   的输入才有机会重新进入 triage 队列。

重算总是从 `corpusCover` 出发再合并剩余占位，所以撤回一个候选既不
会抹掉已确认覆盖，也不会放掉另一个仍在排队/处理中的候选（包括同一
槽位、不同计数档位）的占位。同一个未处理候选重复出现时，
`notePending` 因占位已存在而直接拒绝，保证只排一次。

## 缩减结果为什么可信

`triageInput` 先对原始字节做 3 次复测得到基准证据；缩减判定同样基于
3 次观察：候选必须保住本次缩减需要的新覆盖（`newCover`）和原来的非
负优先级，才被接受；被缩掉的辅助路径不要求保留。`minimizeInput`
返回的字节只有两种可能：原始输入，或最后一个被判定接受的候选——
两者都各自持有完整的 3 次观察。发布给 Hub 的 `data`、`cover`、
`coverSize`、`res`、`execTime` 全部取自这同一个最终候选的观察，不会
把原输入或某个失败候选的指标贴到最终字节上。

`-minimize` 预算到期时，搜索直接停止并返回当前候选；因为每个被接受
的候选在接受时就已经完成 3 次观察，所以到期返回的候选必然带有完整
证据，不需要为了凑结果而无限重试。如果最终候选在（防御性的）重新
观察中崩溃或返回负数，整个候选作废并撤回占位，绝不发布旧覆盖。
空输入同样走这套流程，是合法候选。
